# Vision: Domain-Agnostic Ontology Generation & Interconnected Ontology Web

> From domain-specific tooling to a general-purpose ontology factory.

## 1. The Core Idea

The OntologyExtender started as a tool for extending a **nuclear decommissioning** planning ontology using multi-agent debate.
The end goal is broader:

**Put in any domain documents → get out a well-structured ontology for that domain.**

No pre-existing ontology required.  No domain expertise required from the operator.
The multi-agent team (OntologyEngineer, DomainExpert, Critic) replaces the human ontology engineer for the first 80–90 % of the work, leaving only high-stakes decisions for HITL review.

```
                ┌──────────────────────────────────────────────┐
                │          Domain Document Corpus              │
                │  (PDF, text, regulations, specs, manuals)    │
                └──────────────────┬───────────────────────────┘
                                   │
                          Qdrant (chunked + embedded)
                                   │
                ┌──────────────────▼───────────────────────────┐
                │      OntologyExtender  (this project)        │
                │                                              │
                │  ┌──────────┐  ┌───────────┐  ┌──────────┐  │
                │  │ Engineer │◄►│  Expert   │◄►│  Critic  │  │
                │  └──────────┘  └───────────┘  └──────────┘  │
                │       │    Ont-101 7-phase pipeline    │     │
                │       │    5 debate strategies          │     │
                │       │    6 literature modules (A-F)   │     │
                │       ▼                                      │
                │  ┌──────────────────────────────────────┐    │
                │  │  OWL + SHACL + CQs + YARRRML        │    │
                │  └──────────────────────────────────────┘    │
                └──────────────────┬───────────────────────────┘
                                   │
                          Domain Ontology v1.0+
```

### What makes this domain-agnostic?

| Mechanism | How it adapts to any domain |
|-----------|---------------------------|
| `HITL_DOMAIN_NAME` env var | Sets the domain context for all prompts. Empty = auto-detect from documents. |
| Seed ontology (optional) | If provided, the system extends it. If absent, builds from scratch using Ont-101 Phase 1 (Scope & CQs). |
| Qdrant document source | Any text corpus, chunked and embedded — the pipeline reads whatever's there. |
| Entity linking (Module B) | Auto-discovers matching concepts in BFO, DOLCE, Schema.org, Wikidata. |
| Embedding advisor (Module C) | Semantic similarity-based hierarchy suggestions — no domain-specific rules. |
| Feedback learning (Module F) | Learns from HITL corrections — adapts to any domain's conventions over iterations. |

## 2. The Interconnected Ontology Web

Beyond single-domain ontologies, the vision extends to an **interconnected web of domain ontologies** linked through shared upper-level concepts and cross-domain mappings.

```
                    ┌─────────────────────────────────┐
                    │     Upper Ontology (BFO/DOLCE)   │
                    │   Entity, Process, Quality, ...  │
                    └──────┬──────────┬──────────┬─────┘
                           │          │          │
              ┌────────────▼──┐  ┌────▼────────┐ │  ┌──────────────┐
              │   Nuclear     │  │   Legal /   │ │  │   Medical    │
              │   Decom.      │◄►│   Regulatory│ │  │   Domain     │
              │   Ontology    │  │   Ontology  │ │  │   Ontology   │
              │               │  │             │ │  │              │
              │  Facility     │  │  Permit     │ │  │  Drug        │
              │  Activity     │  │  Regulation │ │  │  Procedure   │
              │  Material     │  │  Compliance │ │  │  Condition   │
              └───────┬───────┘  └──────┬──────┘ │  └──────┬───────┘
                      │                 │        │         │
                      ▼                 ▼        ▼         ▼
              ┌──────────────────────────────────────────────────┐
              │              Knowledge Graph (Neo4j)             │
              │     Instances + relationships across domains     │
              │     Cross-domain links via shared upper concepts │
              └──────────────────────────────────────────────────┘
```

### How interconnection works

1. **Shared upper ontology anchoring**: Module B (Entity Linking) maps every proposed class to BFO/DOLCE upper-level categories. This creates natural alignment points between any two domain ontologies generated by the system.

2. **Cross-domain equivalence detection**: When generating a new domain ontology, the system can compare proposed classes against *existing* domain ontologies (not just upper ontologies) using the embedding advisor. If `Medical:Procedure` and `NuclearDecom:Activity` have high semantic similarity, an `owl:equivalentClass` or `rdfs:seeAlso` link is proposed.

3. **Knowledge graph as integration layer**: The Neo4j knowledge graph stores instances from all domains. Cross-domain queries become possible: *"Which legal regulations affect medical procedures that use radioactive materials?"* — answerable when Medical and Nuclear ontologies share anchoring in BFO and their instances live in the same graph.

4. **YARRRML mappings per domain**: Each domain ontology comes with YARRRML mappings that define how raw data maps to RDF triples. When domains share classes via upper ontology alignment, their YARRRML mappings produce compatible triples automatically.

## 3. The Knowledge Graph Feedback Loop

The most powerful configuration couples the OntologyExtender with a **KnowledgeGraphBuilder** (KGB) module:

```
    Documents ──► Qdrant ──► OntologyExtender ──► OWL v1
                                                    │
                               ┌────────────────────┘
                               ▼
                    KnowledgeGraphBuilder (KGB)
                    ├── Entity extraction (NER)
                    ├── Relation extraction
                    ├── Triple generation
                    └── Neo4j population
                               │
                               ▼
                    Gap Analysis (what entities
                    in KG aren't in the ontology?)
                               │
                               ▼
                    OntologyExtender ──► OWL v2
                               │
                               ▼
                    KGB re-extracts with v2 schema
                               │
                         ... iterate ...
```

Each cycle:
1. **OntologyExtender** produces/refines the ontology (TBox)
2. **KGB** extracts knowledge using the ontology as schema → populates Neo4j (ABox)
3. **Gap Analyzer** compares KG entities against ontology classes → finds uncovered types
4. **OntologyExtender** adds classes for uncovered entity types → improved ontology
5. Repeat until convergence (entity coverage ≥80%, CQ answerability ≥80%, or max iterations)

This feedback loop is the **coupled mode** — the ontology and knowledge graph co-evolve.

## 4. Current Infrastructure

| Service | Port | Purpose | Required for |
|---------|------|---------|-------------|
| **Ollama** | 18135 | LLM inference (qwen3-next 79.7B, llama3.2:3b) | Both modes |
| **Qdrant** | 6333 | Document chunks + embeddings | Both modes |
| **Fuseki (shared)** | 3030 | Seed ontology, class queries, gap analysis | Both modes (optional in standalone) |
| **Fuseki (staging)** | 3031 | Isolated iteration testing | Evaluation only |
| **Neo4j** | 7687 (bolt) / 7474 (HTTP) | Knowledge graph, legal enrichment | Coupled mode + legal enrichment |

### Service independence in standalone mode

Standalone mode runs with **only Ollama + Qdrant**. Fuseki and Neo4j are optional:
- Without Fuseki: No seed ontology introspection, no gap analysis, no SPARQL-based CQ evaluation
- Without Neo4j: No legal enrichment for the DomainExpert, no KG-based gap detection

This makes standalone mode trivially deployable for any domain.

## 5. Benchmarking as Validation

The vision of domain-agnostic generation needs empirical validation. The benchmarking framework is the evidence base:

| Layer | Benchmark | What it proves |
|-------|-----------|---------------|
| **Layer 1** | OntoURL 15-task (Understanding, Reasoning, Learning) | LLM ontology *capability* across 7 ontologies |
| **Layer 2** | OntoURL + debate strategies (Socratic, Dialectical, etc.) | Multi-agent *scaffolding* adds value |
| **Layer 3** | LLM4ACOE head-to-head (vs Agent-OM, NLP-W2V) | Competitive with SOTA ontology construction |
| **Layer 4** | 6-dimension evaluation (taxonomy, relation, axiom, CQ, reasoning, OOPS!) | Generated ontology *quality* |

If the system scores well on OntoURL (which spans 7+ diverse ontologies — pizza, university, conference, people, wine, etc.), it demonstrates genuine domain-agnostic capability.

## 6. Research Questions

The interconnected vision connects directly to the thesis research questions:

- **RQ1** (Reasoning capability): Can a large LLM (qwen3-next 79.7B) handle ontology tasks across domains? → OntoURL benchmark
- **RQ2** (Debate scaffolding): Does multi-agent debate improve ontology quality over single-LLM? → Strategy comparison
- **RQ3** (Best combination): Which model × strategy × methodology combination produces the best ontologies? → Comprehensive matrix
- **RQ4** (Future): Does the KG feedback loop (coupled mode) produce better ontologies than standalone? → Coupled vs standalone comparison
- **RQ5** (Future): Can cross-domain ontology alignment be automated via embedding similarity? → Module B + embedding advisor evaluation
